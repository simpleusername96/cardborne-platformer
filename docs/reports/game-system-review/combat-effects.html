Three priorities

  1. Read the result: same result = same family; different result = different silhouette.
  2. Read the owner: player and hostile versions use color plus one large shape mark.
  3. Read the truth: every warning, radius, and corridor matches the exact runtime area.

AS-IS → approved TO-BE

AS-IS

Shared parts carry too many meanings

Barrier and Ion Field use the same ring at different sizes. Many hit, death, pickup, and secondary events are hidden or use actor and weapon feedback. Effect state has no clear owner or side field.

Approved TO-BE

Meaning comes first

Keep one family for one result. Add clear type, owner, live size, and phase data. Hide small cosmetic effects unless a clear gameplay need defines a new visual.

Locked effect rules

Same result, same family

Use the same base shape for the same result. Do not reuse a ring or burst for a different result.

Different result, different outer shape

Color alone is never enough. Give each result a clearly different large outline or cut.

Owner is two signals

Use role color and one large shape mark. Store owner or side in effect data; the UI does not need to print an owner label.

Exact live area

Code owns live radius, beam width, corridor length, position, and collision. Visuals stretch or scale to that truth; they never invent safety or damage space.

Normal-enemy route UI is forbidden

Do not show a long attack route for a normal visible enemy. Long paths are for bosses, large neutral events, or off-screen fixed devices only.

Ownership boundary

Live combat

The effect and gameplay-cue catalogs own authored EMP and shared live cues. Runtime owns time, damage, protection, position, tint, and exact dimensions.

Upgrade art is not effect art

Upgrades owns the choice and behavior. upgrade/ion_field, upgrade/dash_wake, and upgrade/defense_matrix are card content, not live VFX.

Rule conflict to resolve first

Current visual rules

Shared ring remains permitted

VISUAL_SYSTEM.md permits one shared ring for Barrier and Ion Field, with code changing its color and size.

Approved direction

Barrier and Ion cannot share meaning

Barrier and Ion ring reuse is a conflict. Change the visual rules before implementation; do not add a new asset under the old rules.

Delegated defaults and exclusions

Codex can decide

  • Image size, anchor, spacing, and first role color.
  • Phase timing and data-field names.
  • Which small events use actor or weapon feedback.

Not current assets

There are no production Gravity Pull, Cryo freeze burst, or Meteor effect assets. Define gameplay and ownership before making them.

Your later visual choice

Choose after two or more real-size sheets show the full map, each asset alone, repeated use, stretch, phases, both owners, grayscale, and crowded play. Parts may be mixed. External sources need a clear license and saved source proof.

Effect UI rules

HUD

Show live combat truth only. Keep dash, secondary aggregate, and EMP in the compact action strip.

Warnings

Use a long path only for a boss, large neutral event, or off-screen fixed device. Show the true area before damage.

Hit and kill proof

Restore short feedback when it helps target choice or confirms a kill. Do not cover the field with long cosmetic particles.

Screen priority

Player first, then boss or current target, committed danger, pickups, and cosmetic effects. Every state also needs a non-color cue.
