# 적 밀집 시 버벅임: 최종 결론

## 목적

적 밀집 버벅임의 원인, 이번 구현 결과, 다음 선택과 배포 영향을 간결하게 남긴다.

## 근거 자료

- `2026-08-13-dense-enemy-stutter-evidence.md`
- `2026-08-13-dense-enemy-architecture-options.md`
- 깨끗한 기준·실험·최종 네이티브 성능 JSON과 focused validator 결과

## 한 줄 결론

**원인은 분명하지만, 성능 문제는 아직 해결되지 않았다.** 적이 많을 때 GPU가 아니라
적의 판단·이동·겹침·충돌 계산이 한 화면에 처리할 수 있는 양을 넘는다. 이번에 더 큰
구조 변경도 실제로 만들어 시험했지만 오히려 느려져서, 그 부분은 배포 가능한 코드에서
제거했다.

## Findings / 지금 확실히 아는 것

- 적이 약 192마리를 넘기 시작하면 계산이 밀리는 구간이 나타난다.
- Godot은 밀린 계산을 다음 화면 전에 몰아서 따라잡는다. 그래서 계산이 조금 늦어진
  정도가 아니라 화면이 약 7.5 FPS까지 급격히 무너진다.
- 가장 큰 부담은 일반 적의 스케줄, 판단, 이동, 시야 확인, 주변 적 겹침 처리다.
- 투사체 충돌과 효과가 그다음 부담이다.
- 렌더링은 1차 원인이 아니다. 최종 진단에서도 렌더 CPU/GPU는 약
  `0.72/1.56 ms`, draw call p95는 `98`이었다.

## 이번에 실제로 한 일과 결과

깨끗한 기준 커밋 `4eb3eef3`의 60초 측정은 다음과 같았다.

| 상황 | 물리 p95 / p99 | 화면 p95 / p99 | 결과 |
| --- | ---: | ---: | --- |
| 실제 피크 276마리 | 26.29 / 32.38 ms | 140.51 / 145.69 ms | 실패 |
| 한계 320마리 | 24.60 / 29.73 ms | 143.24 / 146.27 ms | 실패 |

이후 다음 구조를 실제로 구현하고 비교했다.

- 적 상태를 더 촘촘하게 저장하는 방식
- 매번 전체 적을 훑지 않는 영속 스케줄
- 필요한 적만 주변 겹침 목록을 갱신하는 방식
- 투사체와 상태 효과의 packed/sparse 저장
- 별도 표현용 스냅샷

하지만 320마리 짧은 비교에서 물리 p95가 `58.95 ms`까지 나빠졌다. 주요 원인은 새
스케줄과 겹침 갱신 경로 자체의 관리 비용이었다. 사용하지 않는 투사체 복사본과
불완전한 표현 스냅샷도 이득 없이 책임만 중복했다. 따라서 이 실험들은 모두 제거했다.

현재 커밋 `91ab9968`의 5초 준비 + 10초 진단은 물리 중앙값/p95/p99
`18.22/28.79/34.84 ms`, 화면 중앙값/p95/p99 `133.33/143.33/148.51 ms`, 1% low
`6.73 FPS`였다. 짧은 진단이므로 60초 공식 통과 기록은 아니지만, 목표인 물리 p95
`6 ms`와 p99 `8 ms`를 크게 넘는다는 판단에는 충분하다. 이 결과에서 Web 장시간 측정은
중단했다.

## 남겨 둔 개선

- 전투 진입 방향과 시간을 나누는 engagement director
- 적이 앞·옆 여러 방향의 고정 진입 지점으로 접근한 뒤 기존 행동으로 돌아가는 흐름
- 뒤쪽에 빠져나갈 공간을 남기는 두 가지 패턴
- 움직이는 벽 후보를 가까운 셀에서 먼저 찾되, 최종 충돌 판정은 그대로 유지하는 경로
- 재현 가능한 성능·진입 분포 측정과 검증 도구

적이 뒤에서 한 덩어리로만 따라오는 문제는 구조적으로 고쳤고 자동 재생 검증은
통과했다. 다만 사람이 직접 오래 플레이하며 재미와 비율을 조정하는 일은 남아 있다.

## 다음 선택

현재의 정확한 320마리 개별 시뮬레이션과 단일 스레드 Web 조건을 모두 유지하면서
GDScript만 다시 다듬는 경로는 권하지 않는다. 다음 셋 중 하나를 정해야 한다.

1. **Web에 맞는 가상화 — 권장:** 화면 가까이와 전투 중인 적만 정확히 계산하고, 멀리
   떨어진 적은 가벼운 예약 상태로 유지한다. engagement director가 앞·옆 진입 시점에
   정확한 적으로 전환한다. itch.io/Web에 가장 현실적이지만, 멀리 있는 모든 적을 매
   순간 개별 계산한다는 규칙은 바뀐다.
2. **네이티브 전투 코어:** 병목 루프를 C++ GDExtension으로 옮기고 Web용 커스텀
   템플릿과 배포 환경도 만든다. 320마리의 정확한 상태를 가장 잘 보존할 수 있지만 구현,
   테스트, 배포 복잡도가 크다.
3. **지원 밀도 축소:** 동시에 정확히 계산하는 적이나 충돌 빈도를 줄인다. 가장 빠르지만
   현재 제품의 밀도와 규칙을 직접 바꾼다.

Web 게임이라는 현재 제품 성격과 새 진입 전략을 함께 보면 1번이 가장 자연스럽다.
플레이어가 보는 전투는 정확하게 유지하고, 아직 전투에 들어오지 않은 먼 적만
가볍게 관리하는 방식이다.

## 로컬 수정과 배포판

로컬 Godot 코드를 고치면 같은 코드로 만든 GitHub Pages와 itch.io 빌드에도 반영될 수
있다. 다만 자동 반영은 아니다. **커밋 → push → Web export/검증 → 배포 워크플로 성공**이
필요하다. 이번 작업은 로컬 커밋까지만 했고 push나 배포는 하지 않았다. 따라서 현재
공개된 게임의 버벅임은 아직 그대로라고 보는 것이 맞다.

## 한계

- 최종 결과가 이미 네이티브 기준에서 크게 실패해 Web 장시간 성능 측정은 하지 않았다.
- 새 진입 흐름은 자동 재생으로 안전성·결정성·방향 분산을 검증했지만, 대표 구간의 수동
  플레이 기록은 아직 없다.
- 최종 10초 결과는 실패 확인용 진단이며 60초 공식 성능 기록이 아니다.
