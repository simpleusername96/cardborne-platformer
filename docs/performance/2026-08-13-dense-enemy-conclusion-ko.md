# 적 밀집 버벅임: 최종 결론

## 한 줄 결론

**로컬 네이티브판은 현재 48마리 상한에서 기준을 통과했지만, 같은 Web 빌드는 크게
실패했다. 지금 GitHub Pages와 itch.io에 배포하면 버벅임을 다시 배포하는 셈이다.**

## 무엇이 원인인가

이미지나 GPU가 주원인은 아니다. 일반 적의 판단, 이동, 주변 적 탐색과 충돌 계산이
Web 브라우저의 한 프레임 예산을 넘는다. 적이 늘수록 이 계산이 거의 비례해서 커지고,
밀린 계산을 따라잡는 동안 화면도 함께 끊긴다.

## 이번에 좋아진 부분

겹침 계산이 매번 최대 320칸 전체를 확인하던 부분을 실제 살아 있는 적만 확인하도록
바꿨다. 게임 규칙, 충돌, 적 순서와 최대 48마리 상한은 바꾸지 않았다.

같은 최종 커밋 `e0962d7e`의 결과는 다음과 같다.

| 측정 | 물리 계산 p95 / p99 | 결과 |
| --- | ---: | --- |
| 네이티브 48 상한 | `3.344 / 4.127 ms` | 통과 |
| 네이티브 64마리 | `9.623 / 12.062 ms` | 실패, 여기서 상위 실험 중단 |
| 실제 Chrome Web 48 상한 | `11.0 / 13.6 ms` | 실패 |

네이티브의 기술적 한계는 현재 **48 통과, 64 실패**다. 64·96·128마리를 게임에
적용한 것이 아니며, 실제 게임 상한은 계속 48이다.

Web 측정은 1280×720의 일반 Chrome 창에서 했다. 창은 계속 보이는 상태였고,
백그라운드 제한도 없었다. 적은 43마리였지만 화면 p95/p99가 `47.8/63.89 ms`,
1% low가 `14.27 FPS`였다. 측정 방식 때문에 생긴 가짜 실패로 볼 근거가 없다.

## 배포 판단

GitHub Pages와 itch.io 배포는 하지 않았다. 최종 Web 성능 기준을 통과해야 배포한다는
계획서 규칙을 지킨 것이다. 현재 공개판은 이번 로컬 수정이 아직 반영되지 않았다.

## 다음에 필요한 결정

GDScript를 조금씩 더 고치는 방식만으로는 Web 목표에 도달하기 어렵다. 다음 단계는
적의 핵심 계산을 한 곳에서만 관리하는 작은 네이티브 전투 코어를 먼저 시험하는 것이다.
이 방식은 Web용 커스텀 빌드 템플릿과 새 빌드 도구가 필요하므로 별도 승인이 필요하다.

승인 후에도 바로 전체 게임을 갈아엎지 않는다. 먼저 분리된 시험에서 같은 규칙과
결과를 유지하면서 핵심 계산이 최소 2배 가까이 빨라지는지 확인한다. 이 시험이 실패하면
게임 코드와 배포 방식을 바꾸지 않고 폐기한다. 스레드 추가, 기준 완화, 몰래 적 수 줄이기는
이 시험에 포함하지 않는다.

## 기록

결정을 바꾼 네이티브·Web 원본 6개는 커밋, 콘텐츠 지문, 파일 해시와 함께
`docs/performance/evidence/`에 보존했다. 처음 실패한 네이티브 결과와 같은 커밋의 통과
결과를 모두 남겨 좋은 결과만 고르지 않았다.
