# 적 밀집 시 버벅임: 결론

## Purpose / 목적

적이 많아질 때 발생하는 지속적인 버벅임의 원인, 배포판 영향, 다음 해결 방향을 짧게
정리한다. 상세 수치와 대안은 연결된 영문 문서에 둔다.

## Sources / 근거 자료

- `2026-08-13-dense-enemy-architecture-options.md`

## Findings / 결론

주원인은 GPU나 이미지가 아니라 **적 시뮬레이션의 CPU 예산 초과**다. 적이 약 192개를
넘으면 60 Hz 물리 틱의 16.67 ms 예산을 자주 초과한다. Godot이 밀린 물리를 한 화면 전에
최대 8번 따라잡으면서, 20~30 ms 수준의 물리 비용이 133~145 ms짜리 화면 프레임으로
증폭된다. 그래서 적 수가 임계점을 넘는 순간 체감이 급격히 나빠진다.

기존 최적화는 효과가 있었다. 320개 적 기준 물리 중앙값은 약 8%, p95는 약 11%
개선되었다. 그러나 최근 유효 기록의 p95는 여전히 약 21~27 ms이고 목표는 6 ms다. 작은
캐시나 수식 수정만 반복해서는 격차를 닫기 어렵다. 현재 HEAD 자체는 아직 새로 검증하지
않았으므로 이 수치를 현재 버전의 확정값으로 쓰면 안 된다.

## 근거

- 64/128/192/256/320 적 스케일링에서 물리 p95가
  8.44/13.42/18.85/25.16/23.91 ms로 증가했다.
- 192개부터 표시 프레임 p95가 약 135 ms로 붕괴했다.
- 60초 기록은 물리 3,600틱과 화면 450프레임을 남겼다. 화면 한 번당 물리 8틱이다.
- 276개 실제 피크와 320개 한계 시나리오가 모두 실패한다.
- 320개 기록의 렌더 CPU/GPU는 약 0.73/1.61 ms, draw call p95는 101이다.
  렌더링은 현재 1차 병목이 아니다.
- 가장 큰 비용은 적 스케줄 재구축, 판단, 이동, LOS, 겹침 처리다. 투사체 충돌과 효과가
  그다음이다.
- 최근 반배율 카메라 비교는 한 번에 여러 시스템이 바뀐 자료다. 보이는 적 수는
  늘었지만 물리 성능이 악화되지는 않았다. 카메라 범위는 2차 측정 대상이지 주원인으로
  확정할 수 없다.

## Recommendations / 권장 해결책

현재 `VehicleRun` 안에서 미세 최적화를 계속하기보다, **고정 용량 데이터 중심 전투
시뮬레이션 코어**로 옮기는 것이 맞다.

핵심은 다음과 같다.

1. 적 상태를 객체 묶음 대신 `Packed*Array` 열로 저장한다.
2. 매 물리 틱 전체 적을 훑어 스케줄을 다시 만들지 않는다. 영속 큐 또는 타이밍 휠로
   이번 틱에 필요한 적만 처리한다.
3. 생성·죽음·활성화 때 카운터와 큐를 갱신한다. 전체 재계산은 검증용으로만 둔다.
4. 공간 그리드는 셀을 옮긴 적만 갱신하고, 필요한 적만 이웃 목록을 만든다.
5. 상태 효과는 상태가 있는 적만 처리한다.
6. 투사체는 packed 상태와 재사용 가능한 조회 결과를 쓰되, 최초 충돌 판정은 유지한다.
7. 렌더러와 HUD는 현재/이전 시뮬레이션 스냅샷만 받아 보간한다.

이 방식은 현재 단일 스레드 Web 빌드에도 그대로 적용할 수 있다. 먼저 typed GDScript로
만들고, 그래도 기존 6/8 ms p95/p99 목표를 못 맞출 때 같은 경계의 핵심 루프만 C++
GDExtension으로 옮기는 순서가 안전하다.

## 지금 하지 말아야 할 것

- 적·투사체·효과 수를 줄여서 통과시키기
- 물리 catch-up 횟수만 바꾸기
- GPU, MultiMesh, 이미지 크기를 1차 원인으로 보고 재작업하기
- 측정 없이 스레드나 `PhysicsServer2D`로 옮기기
- 현재 Web 배포 조건을 확인하지 않고 데스크톱 전용 GDExtension을 넣기

## 로컬 수정과 배포판의 관계

순수 GDScript, 데이터 구조, 스케줄, 충돌 조회 수정은 로컬에서 고친 뒤 **커밋하고
push하여 GitHub Actions가 성공하면** GitHub Pages와 itch.io의 같은 Web 빌드에 반영된다.
다만 브라우저는 WebAssembly/WebGL 2.0 단일 스레드이므로 개선 폭은 로컬 네이티브와 다를
수 있다. 반드시 실제 export 산출물을 Chrome Performance로 다시 측정해야 한다.

현재 배포 설정은 Web 스레드와 GDExtension을 둘 다 끈 상태다. 스레드나 네이티브 확장은
자동으로 배포판에 적용되지 않으며, 커스텀 Web 템플릿과 호스팅 정책 변경이 필요하다.

## 다음 판단 순서

1. 다른 UI/디자인 세션이 끝난 깨끗한 상태에서 현재 HEAD의 네이티브와 실제 Web 기준선을
   같은 시나리오로 기록한다.
2. packed 상태·영속 스케줄 큐·증분 공간 그리드의 작은 코어를 만들고 기존 적 핫패스보다
   최소 2배 빠른지 확인한다.
3. 행동 결과를 비교하며 적, 공간 조회, 투사체, 상태 효과, 표현 스냅샷 순서로 이전한다.
4. 전체 네이티브/Web 검증 후에도 목표를 못 맞추면 Web 지원 GDExtension을 검토한다.
